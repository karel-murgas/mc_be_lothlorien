# Lothlórien Modular Village — Jigsaw Generation Concept

> **Status (2026-10-07):** prototype implemented, not yet seen in game. Pieces, pools and the `/place`-only structure
> `lothlorien:elven_village` are generated by `tools/build_village.mjs`; offline checks via `tools/village_sim.mjs`.
> Details, limits and the in-game checklist: `docs/TECHNICAL_NOTES.md`, section "Elven village (jigsaw, prototype)".
> The text below is the original concept.
>
> **Walkability rule (owner, 2026-10-08):** every walk surface has >= 1.9 blocks of headroom (also over the NEXT stair tread), every
> deck with a stair has a free walk ring round the trunk, rails stay in their layer and win over leaves, stair rails have up-forward
> posts. Enforced by `.claude/skills/bedrock-modding/scripts/structure_walk.mjs` inside `tools/build_village.mjs`; details in TECHNICAL_NOTES.


## Goal

Generate treetop Lothlórien villages procedurally from modular structure pieces.

The village should:

- be built around Mallorn trees,
- exist mostly above ground,
- use platforms and bridges,
- generate differently each time,
- remain fully connected and walkable,
- avoid relying on random pre-existing Mallorns.

No NPCs, professions, trading, or settlement types are part of this first pass.

---

## Core principle

Use Bedrock's **jigsaw structure system**.

The village is not one large predefined structure.

Instead, it is assembled from multiple small `.mcstructure` templates connected through standardized jigsaw connectors.

Conceptually:

```text
central tree
    │
  bridge
    │
tree platform
   ├── bridge
   │      │
   │   tree platform
   │
   └── house/platform
```

Each structure piece exposes one or more connection points.

The jigsaw generator selects compatible pieces from weighted template pools and attaches them recursively.

---

# 1. Village Mallorns must be part of the structure

Do not attempt to generate a village by connecting Mallorns that already exist in normal biome generation.

Random trees will have:

- arbitrary positions,
- arbitrary heights,
- arbitrary spacing,
- incompatible branch geometry.

Instead, every important village tree should be included inside its own structure template.

Example:

```text
tree_platform_01.mcstructure
```

contains:

- Mallorn trunk,
- crown,
- platform,
- railings,
- bridge connectors.

Therefore the generator always knows exactly where bridges can attach.

---

# 2. Think in nodes and connections

Treat the village as a graph.

Each Mallorn platform is a **node**.

Each bridge is an **edge**.

Example:

```text
          TREE
            |
          bridge
            |
TREE -- bridge -- CENTRAL TREE
            |
          bridge
            |
          TREE
```

The jigsaw system builds this graph recursively.

---

# 3. Define a strict connector standard

This is the most important design rule.

All normal structure pieces should use the same connection geometry.

Recommended initial standard:

```text
normal bridge width = 3 blocks
walking surface = fixed relative Y
railing space included in template
```

A platform connector should always look structurally compatible with a bridge connector.

For example:

```text
PLATFORM

#########
#       #
#       === connector
#       #
#########
```

and:

```text
BRIDGE

connector === ========= === connector
```

If the connector geometry is standardized, Minecraft can rotate and connect modules safely.

---

# 4. Start with only one elevation level

For the first implementation, keep every platform at the same relative elevation.

Do not immediately support:

- arbitrary tree heights,
- bridges climbing upward,
- spiral stairs,
- multi-level settlements.

First prove that flat modular generation works.

Initial rule:

```text
all bridge connectors use the same Y level
```

Vertical variation can be added later with dedicated modules.

---

# 5. Basic structure categories

The first prototype needs only a few module types.

## Start node

Example:

```text
central_mallorn_01
```

Contains:

- large Mallorn,
- central platform,
- 3–4 outgoing bridge connectors.

This is the root of village generation.

---

## Tree node

Examples:

```text
tree_platform_01
tree_platform_02
tree_platform_03
```

Contains:

- Mallorn,
- platform,
- 1–3 outgoing bridge connectors.

These are the main repeating village nodes.

Different variants should vary visually while keeping the same connector standard.

---

## Bridge pieces

Start with only a few lengths:

```text
bridge_short
bridge_medium
bridge_long
```

Each bridge has:

- one connector at each end,
- three-block-wide walkable path,
- railings.

Avoid curved bridges initially.

---

## End pieces

Every branch needs a way to stop.

Examples:

```text
small_balcony
lookout_platform
railing_end
```

Without end pieces, the generator may leave visually unfinished connections.

---

# 6. Template pools

Group compatible pieces into template pools.

Conceptually:

```text
lothlorien:village_start
    central_mallorn_01
    central_mallorn_02
```

```text
lothlorien:bridges
    bridge_short
    bridge_medium
    bridge_long
```

```text
lothlorien:tree_nodes
    tree_platform_01
    tree_platform_02
    tree_platform_03
```

```text
lothlorien:endcaps
    lookout_platform
    balcony
    railing_end
```

Weights can later control how often each variant appears.

---

# 7. Recommended connection flow

Keep the connection logic simple.

Example:

```text
CENTRAL TREE
    ↓
bridge pool
    ↓
tree node pool
    ↓
bridge pool
    ↓
tree node OR end pool
```

A tree node may expose several connectors, causing branching.

Example:

```text
             bridge → tree
            /
central tree
            \
             bridge → tree → bridge → tree
```

---

# 8. Limit village growth

Use jigsaw recursion depth and maximum generation distance.

The generator must not expand indefinitely.

For the first prototype, use a deliberately small depth.

Conceptually:

```text
depth 0
central tree

depth 1
bridges

depth 2
secondary trees

depth 3
additional bridges/end pieces
```

Once connectivity works reliably, increase depth gradually.

---

# 9. Collision handling

Structure generation must reject pieces that overlap existing generated village pieces.

This is another reason not to use arbitrary existing Mallorns.

Each structure template should have sensible bounding dimensions.

Avoid enormous crowns extending far outside the functional tree node bounding area unless tested carefully.

For village-ready Mallorns:

- keep bridge connection zones clear,
- keep foliage away from neighboring connector space,
- avoid large branches crossing likely bridge paths.

---

# 10. Village-ready Mallorn variants

The normal procedural Mallorn generator can produce a special class of trees for village use.

These must obey stronger constraints than wild Mallorns.

Village Mallorns should have:

- predictable trunk center,
- known platform height,
- clear area around platform,
- clear bridge connector directions,
- controlled crown spread near bridges,
- safe walkable geometry.

Example generator parameters:

```text
platform_height = fixed
connector_clearance = 5 blocks
trunk_center = known
minimum_clear_radius = fixed
```

Generate multiple candidates and save the good ones as `.mcstructure` variants.

---

# 11. First prototype asset set

Keep the first test extremely small.

Create:

```text
1 central Mallorn
2 secondary Mallorn/platform variants
2 bridge lengths
1 lookout/end piece
```

Total:

```text
6 structure templates
```

That is enough to prove the system.

---

# 12. First prototype generation target

Example result:

```text
              TREE
               |
             bridge
               |
TREE -- bridge -- CENTRAL TREE
               |
             bridge
               |
            LOOKOUT
```

Different runs should produce different combinations while remaining connected.

---

# 13. First-pass success criteria

The jigsaw system is considered proven when:

- the structure generates naturally,
- the central tree always appears,
- secondary Mallorns connect through bridges,
- structures rotate correctly,
- bridges meet platforms exactly,
- no large gaps exist,
- no inaccessible platforms exist,
- no major structure overlaps occur,
- branch generation terminates cleanly,
- repeated generation produces different layouts.

Do not add buildings or NPC logic until these conditions are reliable.

---

# 14. After the prototype works

Expand gradually.

Recommended order:

1. more Mallorn variants,
2. more bridge lengths,
3. junction platforms,
4. house/platform nodes,
5. gardens,
6. vertical bridge/stair modules,
7. multi-level generation,
8. decorative variations.

The important rule is:

> Increase visual complexity only after connectivity is stable.

---

# 15. Architecture summary

```text
                    START POOL
                        │
                 central Mallorn
                        │
                 bridge connectors
                        │
                  BRIDGE POOL
                        │
                  TREE NODE POOL
                    /        \
              connector    connector
                  │             │
             BRIDGE POOL   BRIDGE POOL
                  │             │
              TREE NODE      END CAP
```

The village is therefore a recursive network of:

```text
Mallorn node
→ bridge
→ Mallorn node
→ bridge
→ Mallorn node / end
```

This is the first implementation target.

# 16. Loop closer (round 2, owner decisions 2026-10-09)

A jigsaw village is a tree; `scripts/loop_marker.js` + `village_loop.js` close loops at runtime (details and numbers: `docs/TECHNICAL_NOTES.md` P7 to P7d).
Owner decisions: (1) two facing plain platform rims get a bridge (F1, markers on rim runs); (2) exits may be as close as 2 apart, 2..4 apart is a flat deck (F2);
(3) direct bridges may shift 8 sideways (F3); (4) a "plaza" deck joins two close, sideways offset balcony ends, always on a pier (F4, approved on the gap5 case);
(5) L-joins: leave A, straight bridge, a square 5 x 5 railed landing on a pier, turn 90 degrees, straight bridge into B, no diagonals (F5);
(6) clutter rule: no new join within 2 cells of another structure's deck, one join per pair, never through other structures. Standing rules: arched slab bridges with a
continuous slab body, continuous rails, light >= 8 on every walk cell, headroom and walkability by the shared checker. Status: simulator and unit tests only.
